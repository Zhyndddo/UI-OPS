## RLS — what the SQL does
File: `sql/pending/rls-round556-enable-baseline.sql`. Run it **section by section** (select the section → Run), smoke-testing in between.

| Section | What | Risk |
|---|---|---|
| 0 | helper functions + `rls_state_r556` (records what each table was before) | none |
| 1 | Batch A: scratch/backup tables (`_r5xx`, `*_backup`) | lowest |
| 2 | Batch B: all tables except the core list and profiles | low |
| 3 | Batch C: releases, tickets, ticket_tabs, notifications, magic_links, app_settings, global_settings | medium |

Baseline policy `staff_all_r556`: signed-in staff can do everything on those tables (same as today). Logged-out visitors get nothing. Service-key routes (cron, admin API, short links, /api/magic) bypass RLS.

### profiles rules (section 5)
- Everyone signed in can read the roster.
- Changing **role, team, subteam, email, login link** on a profile: **dev** can do anything; **admin** can change role/team/subteam of non-dev people only (never a dev, never email/login link, and cannot mint a dev); everyone else cannot. A person can still change their own harmless fields (notification toggle, snooze, name).
- First login: a person can link *their own* unlinked profile (matched by email) — and nothing else in that same update.
- Adding a person from Config: dev (anyone), admin (not a dev), team lead (only an "exc" in their own team). Nobody can delete a profile from the browser (the admin API route still can).
- SQL editor / service key are unaffected (no signed-in user → the guard steps aside).

## Tested
On a scratch Postgres with the Supabase `auth.uid()` / `auth.jwt()` shape: 28 checks across staff / team lead / admin / dev / first-login / logged-out all behaved as listed (blocked, allowed, or "0 rows"); section re-runs are safe; undo turns tables back off.
