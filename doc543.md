# Round 543 - egress pass 3: Cost Marketing

Problem (measured 22 Oct): Cost Marketing downloaded every TikTok-Channel/Ads row of media_booking_entries (8 paged requests, ~455 kB) + media_booking_content_entries (~107 kB) per page load, just to count them.

Fix:
- NEW sql/pending/add-round543-cost-mkt-entry-totals.sql - two read-only, staff-only functions (cost_mkt_entry_totals, cost_mkt_content_totals) returning the same counts grouped on the server (entry count + sum of quantity per release/category/brand/platform/subchannel; content row count + sum of count_posts per release/package/category/brand/platform).
- app/workstation/cost-mkt/page.js - load() calls the two RPCs; addedFor() and the content-entry fallback read the grouped rows with the identical matching rules. If the SQL hasn't been run the page falls back to the old full download (grouped client-side), so push/SQL order doesn't matter.
- Verified on a scratch Postgres: 19,200 added/booked lookups, old (raw rows) vs new (grouped) = 0 mismatches.

Run: push the code, run the SQL (either order). Re-measure Cost Marketing in DevTools (supabase.co/rest filter): expect the 8x media_booking_entries requests (57 kB each) to become 1 small rpc call; was 875 kB total.

Booking Board finding (no change this round): the two ~89 kB media_booking_entries requests are NOT a double load - they are the two pages of one fetch (fetchAllRows pages at 1000 rows; the 50 releases on a page carry >1000 entries incl. the link text). Real savings there need either a smaller page size (50 -> 25) or lazy-loading the link text on cell expand; both change behaviour, so left for the owner's call.

Still open from the egress plan: Task Table (releases queried 5x), Report (163 kB releases select), Auth egress ~31 MB/day.
